# Opt-in native JJ stack construction and submission

Only load for explicit stack intent or a standing stack preference. Before ordinary Step 3 perform probing, topology, and construction only; Step 5 exclusively owns publishing and description application. Use JJ bookmarks/ancestry and repository-scoped gh, not a harness or Git workspace/stack bridge. Follow `context.md`'s absolute cwd and GIT_DIR requirements for every command. See `gh-stack-cli.md` for identity and topology safeguards.

## Probe and topology

Verify gh authentication, repository stack capabilities, exact remote/base/head identities, and push authority. Missing capabilities or unresolved topology are residuals, not permission to guess. Explicit stack intent (or a mandatory standing preference) makes inability to preserve a stack a hard stop; soft intent may report the residual and use single-PR flow. Without an explicit current request, one logical change or artificial slices should use single-PR flow; explicit requests are not refused on those grounds.

Record original feature bookmark, exact tip and owned working changes before probing. Resolve a named parent by PR number where present, verify its exact current head, author, repository and ancestry, and preserve the requested parent. An existing colliding bookmark with a different target is a residual; never reset it. A standalone parent can remain an untouched trunk, or be adopted as bottom layer only when authored by the current user. Branch-only parents are trunks. Preserve existing managed topology; if the named parent cannot safely accept a layer, report it instead of silently selecting the stack top.

An explicit upstack layer uses its authoritative parent: verified remote tip when current, verified local parent when its newest work is not yet published. Never hardcode origin or substitute the default base for a named parent. Create a collision-free bookmark at that exact tip with `jj bookmark create <layer> -r <verified-parent-tip>`, and use `jj new <verified-parent-tip>` only when doing so preserves unrelated/excluded work and the planned owned changes. On tracked, ignored, or untracked collisions, stop (pipeline: residual); never stash/discard/remove them. No workspace creation is necessary for stack construction.

## Retrospective construction

Inspect the complete original change set against the exact resolved base: committed, tracked and untracked owned changes. Derive the smallest useful coherent linear layers, foundation first, each independently reviewable against its parent. Use whole files or existing commit boundaries, never forced hunk splits. Multiple materially different safe topologies require a concise bottom-to-top decision; pipeline reports the proposal without guessing. Hunk partitioning and rewriting published history require distinct explicit authorization; pipeline stops with that residual.

When starting on the default bookmark without a named parent, follow `branch-creation.md`, including its unpushed-local decision. For an existing feature, fetch and verify the actual selected base; do not mistake feature commits for local-default commits or carry the whole feature tip into the bottom layer. A verified locally materialized PR head may be the parent even without a remote bookmark.

Create a recovery bookmark at the original tip before rearranging. Preserve all original owned tracked/untracked changes until the constructed top is verified complete; store any required evidence under workspace-local `.tmp/`. Excluded paths belong to no layer: never save, move, restore or commit them. If an operation would affect them, stop. Use path-scoped `jj commit -m "<message composed from the standards above>" -- <layer-owned-paths>` and construct each next layer on its immediate verified parent. Apply the complete `commit-and-push.md` message standard before every layer's message, reading the full Go guide and comparing full recent JJ subjects and bodies from the relevant history anchor. Preserve any already-known single-unit U-ID as semantic content without forcing syntax.

For already coherent committed boundaries, create/reuse one bookmark at each verified tip. Reuse the original feature bookmark only when its unchanged tip is a planned layer. Verify complete bottom-to-top ancestry, layer diffs, and that the constructed top equals the complete original intended change set minus exclusions before publishing. Retain recovery references.

## Submit: Step 5 only

Apply the project publishing gate to each exact final layer. Resolve archival first; if requested, stop with a residual before submission until archival has a safe stack-aware route. Do not disable it silently or add an unplanned post-submit explainer commit.

Reverify remote, head repository, bookmarks, commits, existing PRs and authority. Push each intended bookmark with `jj git push --remote <verified-remote> --bookmark <layer>`. For each layer, query its exact PR in the base repository and match head owner/name; nonzero query status is unknown, not absence. Create only genuinely absent PRs with explicit immediate-parent `--base`, exact `--head`, and `--body-file` using `apply-and-handoff.md`; preserve existing stack titles/bodies unless an update is authorized. Existing drafts remain drafts unless explicitly authorized ready; never silently mark user work ready. New ready PRs follow the requested shipping intent.

Map every created PR URL to its verified head and parent. Run normal PR-mode composition per URL (never whichever bookmark happens to be current), then apply descriptions for newly created PRs. Optional existing-PR rewrites still need approval; a decline does not block authorized handoff. Authorized babysit factual refresh is maintenance without another ask.

Report and hand off the bottom open non-draft PR, default `posture:stack-ready`, or `posture:stack-land` only for explicit land intent; pipeline passes stack-wide scope. Draft-only output is a hard residual when babysit is enabled. Respect standing opt-outs and watch boundaries. Landing belongs to the stack-aware `ce-babysit-pr` lifecycle, never independent per-member merges or a Git-backed stack bridge. Missing lifecycle support is an explicit blocker, not permission to weaken coverage.
