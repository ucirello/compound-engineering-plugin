# Opt-in stack construction and submission

Before Step 3, run Probe, Topology, and Retrospective construction only; this replaces ordinary Step 3. Step 5 alone runs Submit. A **residual** is an unresolved item reported to the user or calling pipeline instead of guessed.

## Probe

Check `gh` availability and `gh stack link --help`; read `references/gh-stack-cli.md` for the GitHub-only link procedure. Resolve authorized head/base repositories and push remote with `references/context.md`. If the required stack capability is missing, or the host reports stacks unavailable, stop with a residual for explicit or standing required stack intent; only soft intent may fall back to the single-PR flow. Never silently collapse an explicit stack into one PR.

## Topology

Resolve named parents by explicit PR URL/number when possible, without changing `@`. Verify the parent PR's repository, head branch, exact `headRefOid`, author and stack membership. A branch-only parent may serve as an untouched trunk only after its owning remote and exact tip are verified. Resolve a PR head using its named repository/remote and exact JJ fetch or a locally available matching commit; never repoint an unrelated same-name bookmark or substitute a nearby SHA.

- **Managed parent** — retain the verified GitHub stack's order and add only above its actual top. A named interior parent is a residual, not permission to choose the top instead. A GitHub-only linked stack may have no local tracking; use the ordered PR URLs and JJ bookmarks.
- **Standalone parent** — keep it as an untouched trunk or, only when its PR author is the current user and the intended topology includes it, adopt it as the bottom layer. Use that PR's verified base as trunk when adopting.
- **Unproven membership, ambiguous ownership, or incompatible cross-repository base** — stop with a residual. An absent current checkout is not evidence of standalone status.

When a current managed stack is verified, preserve it. Otherwise use retrospective construction. If the user did not explicitly ask for a stack and only one useful change or artificial slices are possible, use the single-PR path. For a requested new upstack layer, use the verified immediate parent tip. Prefer the fetched authoritative tip; use a verified unpublished local parent only when it is explicitly in the publication plan and will be published first. Never fall back to the default. Pass names as literal arguments, not interpolated command syntax.

## Retrospective construction

Inspect the complete intended change against the exact bottom parent: existing commits and all authorized working-copy paths. Choose the smallest useful set of linear, independently reviewable layers in dependency order. Use whole-file groups or existing commit boundaries. When several valid topologies change review boundaries materially, ask with a bottom-to-top proposal; pipeline reports the proposal as a residual. For hunk partitioning or published history rewrite, obtain explicit separate approval; pipeline stops. No approval is needed for the unambiguous local construction already requested.

Starting on the default bookmark with no named parent, resolve the base and unpushed-default decision in `references/branch-creation.md`. Otherwise use the exact verified task base or named parent's tip, not a local default. Record original tips, working-copy change, exclusions and full intended diff; preserve the original tip through a recovery bookmark before any restructuring. Copy/replay only verified unpublished commits onto the intended parent with native JJ (for example, `jj duplicate` with explicit revisions and destination) rather than altering unrelated history. Do not let reconstruction move existing bookmarks or expose excluded work. If clashes, conflicts or dirty/ignored work make a proposed move unsafe, stop and leave all work recoverable.

For existing commits matching the layer plan, create or verify a bookmark at each exact layer tip. Reuse a feature bookmark only for the correct layer and expected ancestry. For working-copy groups, use `jj commit -m "<message composed from the standards above>" -- <layer-owned-paths>` to commit each group in order while the remainder stays in `@`. Each layer must descend from its immediate parent's verified tip; create its unique bookmark at the exact resulting commit (`jj bookmark create "<layer>" -r "<layer-tip-id>"`). No `exclude:<paths>` enters any layer. Before composing any layer message, follow **Compose each JJ change description** in `references/commit-and-push.md` in full: read the guide and compare several complete descriptions at the verified task history anchor, follow local syntax, and include the applicable plan unit only when already known. Verify all exact layer boundaries, tree diffs, conflicts and the top's complete intended change against the original inspection before submission.

## Submit

Resolve the `pr_teaching_archive` / `archive:on|off` gate. If archival is on, stop before submission and report that the stack does not support archiving after publication; do not silently turn it off. Apply the **Project publishing gate** to all exact tips to be pushed. Reverify each bookmark, remote, push authority, existing head ancestry and expected PR base. Push only the verified layer bookmarks to their verified head remote, using `jj git push --remote "<head-remote>" --bookmark "exact:<bottom>" --bookmark "exact:<next>" …` when they share that remote. Do not claim all-or-nothing success: after any failure, re-read the exact remote OIDs, report what was written, and stop rather than blindly retrying or overwriting.

Resolve each layer's PR bottom-to-top by exact head repository and branch. Use the normal no-duplicate check and explicit `--base "<immediate-parent-branch>"` for creation; verify the head/base mapping and keep unrelated existing PRs intact. If a parent branch cannot be used as a base on the target GitHub repository, stop before PR creation rather than substituting the default. Keep existing drafts unless explicitly authorized to mark them ready. If any existing layer is an unauthorized draft, keep the new layers draft too and treat the draft outcome as a residual before default babysitting. Otherwise create new layers ready unless the user or project asks for draft.

Map each newly created PR to its explicit URL. Compose and apply its title/body against the exact layer range using Step 4 and the usual body-file rules. Preserve existing layers' title/body unless explicitly authorized to rewrite; the pipeline default is no optional rewrite. Link the verified open layers using `references/gh-stack-cli.md` with PR URLs only. Verify the linked identity and ordered membership, preserving any existing downstack members. Report a partial result with URLs, pushed OIDs, and failed operation if any push/create/edit/link is incomplete; do not rerun creation blindly.

Return the ordered PR metadata and verified stack identity, including the bottom open non-draft URL. A draft-only submit is a hard residual before default babysitting, not a completed handoff. In Step 5, use `posture:stack-ready` by default and `posture:stack-land` only on explicit land intent; never treat either as blanket final merge approval.
