# Step 1 detail: forge check, PR resolution, chain classification, JJ workspace, watch mode

## Prerequisites

The loop runs `gh`, `jj`, read-only `git log` for local message conventions, and a bundled Python helper against a local JJ workspace with filesystem access. `gh` needs the backing repository path; in a non-colocated workspace set `GIT_DIR="$(jj git root)"` for each `gh` invocation. A runtime without these capabilities cannot run this skill — say so and stop rather than half-running.

## Step 1: Confirm GitHub, resolve the PR, pick an execution mode

**GitHub only.** This skill and everything it delegates to speak GitHub's API (`gh`, review threads, Actions). First require `jj workspace root` and `jj git root`, then confirm `gh repo view` succeeds (including configured GitHub Enterprise). If it fails, inspect `jj git remote list`; a non-GitHub URL or an unresolved repository is a stop. Tell the user `ce-babysit-pr` is GitHub-only and do not proceed into failing `gh` calls.

Then resolve the target PR from the argument (number/URL) or the unique local bookmark pointing at `@` and backed by an open PR. JJ has no current bookmark, so never infer the target from working-copy position alone. If no open PR exists, report and stop. Resolve draft state with the PR. For an automatic calling-skill handoff without an explicit user watch-mode token, this check must be the stateless pre-bootstrap read `gh pr view --json isDraft` — never `snapshot --start-invocation`, which mints a new invocation and would supersede a watch a user explicitly authorized on that draft — and a draft target reports its draft status and stops here, before any bootstrap or watcher, per the "Draft PRs are opt-in" boundary. On user-invoked runs the first snapshot's emitted `pr_is_draft` serves as the ongoing signal.

**Automatically classify the target's PR chain; never rely on the user to announce a stack.** Export JJ bookmarks before the read-only local `gh stack view --json` probe and accept its result only when it contains the target PR. If the manager cannot identify an exported bookmark without moving the working copy, use the read-only GraphQL fallback. A successful null stack means `pr_chain.manager_status == "absent"`; uncertain auth, transport, rate-limit, schema, or default-bookmark evidence means `"probe-error"`. When no manager is confirmed, ordinary open-PR base/head relationships distinguish an independent PR from a manual dependency chain. Discovery never checks out or imports a stack and never changes remote state.

**Only when the fresh snapshot has `manager_status == "confirmed"` may stack-wide continuation activate; no other classification authorizes it.** A manual dependency chain never activates stack-wide continuation: keep it target-local even when its base/head topology resembles the manager's ordered branches. `probe-error` also stays target-local and mutation-conservative until a later snapshot positively confirms the manager. Discovery still runs for every babysit — posture does not disable confirmed-manager detection or Step 7 upstack maintenance.

For a confirmed managed stack, inspect the manager's ordered entries once before choosing the active layer; this is read-only orientation, not multi-PR monitoring. Resolve **posture** per the table above before semantic work. If posture is still `target` and the requested middle PR has an unsettled downstack layer, offer once to begin at the lowest unsettled non-draft layer and proceed upward (`stack-ready`), with target-only as the alternative; do not silently redirect semantic work to another PR. If posture is already `stack-ready` or `stack-land` and the requested PR has an unsettled downstack layer, begin at the lowest unsettled non-draft layer without asking (downstack-to-upstack). If all downstack layers are settled, begin on the requested PR. When the requested PR already looks ready or later settles under `target`, offer once to continue to the immediate open non-draft upstack layer if it needs work (accepting selects `stack-ready` for the rest of the run). That one-time offer expands semantic babysit scope on an already confirmed managed stack — it is **not** a proactive suggestion to create or adopt PR stacks. An explicit request to babysit the managed stack counts as `stack-ready` acceptance, so do not ask redundantly. In `mode:pipeline`, which cannot ask, continue beyond the requested PR only when the invocation already supplied `posture:stack-ready`, `posture:stack-land`, or equivalent stack-wide scope; otherwise return the next candidate as a residual.

Once `stack-ready` or `stack-land` is in effect, that posture authorizes sequential semantic babysitting through the confirmed managed stack without asking again at each layer. Keep one target and one watcher. At transition, stop the watcher, fetch and verify the next layer's remote bookmark, then create or edit a dedicated JJ change based on it. Initialize that layer with `--continue-invocation`, the original invocation ID/start/budget, the prior layer's dead-time carry, and the same posture. Never replace unrelated work in `@`, enter an unrequested draft, or advance past a human blocker. Reconfirm manager membership before each transition.

**Verify the JJ workspace targets the PR bookmark before delegated mutation.** Resolve `gh pr view <ref> --json headRefName,headRefOid,isCrossRepository,headRepositoryOwner`, identify the actual JJ remote for that head repository, and run `jj git fetch --remote <head-remote>`. Require `<headRefName>@<head-remote>` to resolve to `headRefOid`; track it with `jj bookmark track <headRefName> --remote <head-remote>` when appropriate, and require the local bookmark to be unconflicted. JJ has no active bookmark: `@` must either equal the PR head or be one clean, dedicated working-copy change descended directly from it. Use `jj new <headRefName>@<head-remote>` to create that change or `jj edit <dedicated-change>` to resume it. Refuse to replace unrelated content already in `@`. Before push, describe the intended revision, move the local bookmark to it with `jj bookmark move <headRefName> --to <revision>`, and use `jj git push --bookmark <headRefName> --remote <head-remote>`; JJ's remote-bookmark lease checks must remain enabled. No push access, a conflicted bookmark, an unexpected remote move, or ambiguous fork routing is a stop rather than permission to overwrite the PR head.

At every point that composes, edits, validates, or recommends the JJ change description, apply this instruction: Based on https://go.dev/wiki/CommitMessage and on past commit messages that you can see in `git log`, compose commit messages adherent to the present standards. Local instructions and `git log` syntax win; do not use fixed message syntax or canned examples, and keep `<message-derived-from-local-conventions>` as the neutral placeholder until composition.

Then establish **how the watch sustains itself** — a skill can't be re-invoked by magic once its turn ends, so *you* set up the loop. **The default is a self-sustaining, in-session watch: you do not do one tick and hand back a resume command.** Read `references/watch-loop.md` for the mechanics, then:

**User-runnable resume syntax.** Whenever this skill prints or copies a resume invocation, default to `/ce-babysit-pr <url>` and, when the run posture is not `target`, append the same `posture:stack-ready` or `posture:stack-land` token so checkpoint / durable / session re-entry keeps stack scope. Use `$ce-babysit-pr <url> [posture:…]` only when the active host is Codex or explicitly documents dollar-prefixed skill invocation. Render only the invocation as inline code and output one form only.

- **Self-sustaining in-session watch (default).** Start `pr-snapshot watch` in the background and wait for its sentinel with the available background-and-wake capability. On each wake run one reasoning tick, persist, and re-arm. Do not collapse judgment into a shell loop.
- **Checkpoint.** Only when no background-and-wake capability exists, run one tick, persist, report that monitoring is paused, and print the resume invocation. Never fake persistence with a foreground sleep or detached process.
- **Pipeline** (`mode:pipeline`, set by an orchestrator like `lfg`) — run **bounded synchronous ticks in-line**: the orchestrator is the scheduler, so loop ticks yourself (snapshot → act → re-snapshot) until the **pipeline stop** (Step 3), then return. Fully non-interactive. See "Pipeline mode" below for the deltas — a different stop condition, native residual surfacing, and a structured return — and read `references/watch-loop.md` for its bound.

**Durability.** Re-invocation from the same workspace resumes from `.tmp`. An unattended scheduler must run from that workspace and use the host-rendered resume invocation. Persist consequential decisions because a fresh run has no conversation context. Honor an explicit mode; otherwise select from available capabilities.
