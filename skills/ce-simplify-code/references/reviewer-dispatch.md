# Reviewer Dispatch

Read this before dispatching the Step 2 reviewers, including a combined or structural reviewer.

**Delegation permission.** Step 2 explicitly requests reviewers. Under a user-or-skill delegation rule this is sufficient; do not ask again. A higher-priority prohibition, unavailable tool, or actual denial still applies. Do not bypass it via shell or another harness.

**Model selection.** Model override permission is separate from delegation permission. Resolve the user's or project's named model first, then the configured role model, then the balanced mid-tier default (Sonnet class). They can name it by the subagent's tier, by its prompt-asset name, or for the subagents being dispatched. When the override is both permitted and supported, resolve the available model and variant using `opencode.models` and pass it to the native subagent tool. If the host requires an explicit user model request and none was made, omit the optional `model` argument even when configuration suggests a model. Use an inherited-model reviewer when it can satisfy the pass; disclose unmet model intent. Separate reviewers on the same model are not cross-model coverage; an unmet required different-model pass or fixed route leaves coverage incomplete.

A generic subagent is one whose whole brief is the prompt you send it. When the host's subagent tool makes you name an agent, use only a name you have seen the host list, and list its agents before the first dispatch if you have not. Pick the plain one that adds no role of its own, which still counts as a generic subagent. Never pick a specialist, such as a reviewer or worker agent, whose own role prompt, output format, or tool limits would replace or narrow your prompt.

**Bounded dispatch.** Each reviewer starts in a fresh subagent whose context holds only its own rubric and inputs. The one exception is the combined reviewer that `references/single-pass.md` chooses below a size cutoff, which is itself one reviewer. Otherwise do not combine reviewers in one prompt, and do not send a reviewer to an agent that already ran another. Queue the reviewers and launch only as many as the harness accepts at once. When the harness is full, wait for a running reviewer to finish, release it when supported, and launch the next. A concurrency or active-agent-limit error means the harness is full, not that the reviewer failed: leave the reviewer queued and retry after a slot frees.

**Nesting and fallback.** Check the effective OpenCode `experimental.subagent_depth` in the active runtime configuration (`/api/config`); a configured limit does not imply remaining depth. If dispatch fails, use the actual error to distinguish exhausted depth, temporary concurrency limits, denied delegation, an unsupported or rejected model argument, and a missing tool. Do not retry a denied operation; correct a model argument only when the resulting invocation is allowed and preserves the required route. When native dispatch is unavailable or cannot recover through active work, supported release, or an allowed correction, the coordinator may run that pass inline using the same prompt asset and disclose the substitution. Never count inline review as independent and never use it to satisfy a required independent or fixed-model pass. Report any such missing pass as incomplete.

**Agent lifecycle.** Collect terminal outcomes, including failures, before cleanup. Close or release review-owned agents when the harness provides caller-owned cleanup, before refilling slots, advancing stages, or returning. Do not message completed agents with no remaining work. Do not infer released capacity from completion or interruption, or invent cleanup operations.

**Permission mode.** Omit the `mode` parameter on the dispatch call so the user's configured permission settings apply.
