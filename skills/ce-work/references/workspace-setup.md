# Workspace Setup

Read this after input triage identifies code work and before any branch move, implementation edit, worker dispatch, or commit. It covers choosing a writable checkout, clarifying the plan, placing the branch, recording what was already in progress before work began, handling a unit that must edit an already-dirty file, and setting up the task list. Return to the main `SKILL.md` flow: the canonical checkout, the branch, the pre-work paths and commits, the exclusions, and the task state.

## Writable Checkout

Repo-local implementation writes require a writable JJ workspace. Before treating the current working directory as the project, confirm its absolute root with `jj workspace root` and verify you can edit it. If this session has no writable workspace, but the user named a repository and the harness exposes a remote repo-work surface with one, run implementation there and treat it as canonical for verification, changes, and handoff. Otherwise report no writable workspace; do not synthesize file changes from a non-repository scratch directory. Run every JJ command from the target absolute root (`(cd "$workspace_root" && jj ...)`, or Python `cwd=workspace_root`), not merely with `jj -R`. For repository-scoped GitHub calls use `(cd "$workspace_root" && GIT_DIR=$(jj git root) gh ...)`. Keep all temporary files, including fallback/error artifacts, under local `.tmp/` and verify that directory is ignored.

## Prepare the Work

1. **Read Plan and Clarify** _(skip for a bare prompt)_ — read `references/work-intake.md` for how to size the read, what to pull from the plan, and when to stop and ask. Treat the plan as a decision artifact, not an execution script: ask anything unclear before implementing rather than after. **Do not edit the plan body during execution** — progress lives in JJ changes and the task tracker, and legacy `- [ ]` / `- [x]` marks or a `status:` field are not state.

2. **Setup Environment**

   Two things must hold before the first edit: the work uses a feature bookmark, and nothing the user did not offer up gets finalized or published by this run. Neither routine authorized action needs a second approval. Preserve all unrelated work and say what bookmark was selected in one line.

   **Bookmark.** Determine the default branch using repository metadata, for example `(cd "$workspace_root" && GIT_DIR=$(jj git root) gh repo view --json defaultBranchRef)`; otherwise inspect verified remote bookmarks for `main` or `master`. Inspect `jj bookmark list` and the ancestry of `@`/`@-`; JJ has no checked-out branch, and an empty `@` directly above a bookmarked commit is already on that line of work.

   If only the default bookmark applies, or the feature target is uncertain, select a new feature bookmark named from the plan/work and verify name collisions before `jj bookmark create <feature> -r <verified-revision>`. When a remote default exists, fetch with `(cd "$workspace_root" && jj git fetch --remote origin --branch "$default")` first. Use its exact verified remote revision as base only when no local changes/commits must remain visible. Otherwise preserve the current ancestry and working copy; never discard or rebase unrelated local work merely to match the remote. Record the selected base and feature bookmark, then verify with `jj bookmark list`. Never advance the real default without explicit authorization.

   Otherwise continue on the invoked feature bookmark without renaming it or asking. Use `ce-worktree` only when requested this session, except for the isolated-worker contracts in `references/execution-strategy.md` and `references/cross-model-execution.md`. Detect existing isolation first and reuse its verified existing name; do not recreate or rename it. For newly created `ce-worktree` workspaces, follow the stable date-prefixed name, matching destination basename, collision, explicit `jj workspace add --colocate`, colocation verification and harness-session adoption requirements in the cross-model reference. Its retirement safeguards also govern any authorized run-owned cleanup; use `jj workspace remove` from a surviving absolute root, never a Git fallback or forget-plus-delete. Harness-owned lifecycle authority remains intact. Unsupported required naming/colocation blocks creation safely.

   **Pre-work scope.** Before editing, record `jj status`, `jj diff --summary`, tracked files via `jj file list`, and a filesystem inventory of ignored/untracked candidates. Inspect local-only ancestry with `jj log -r '<verified-remote-default>..@'`; record "unknown" without a verified remote. Nothing pre-existing is yours to finalize or publish. Preserve it untouched: no stash, discard, or implicit inclusion. Enforce this without asking the user to choose:
   - Incremental JJ changes are path-limited to work-owned files, so untouched WIP never enters the finalized change; the standalone handoff passes every pre-work file this run did not finalize as `exclude:<paths>`, and ships locally via `ce-commit` when pre-existing unpushed commits are on the bookmark (`references/shipping-workflow.md`).
   - A unit that must edit a file that was already dirty is the one case a commit cannot separate. Ask once, at the first commit that would include such a file, and cover every such file in that one question: commit those files with the user's edits included, or leave them uncommitted (an exclusion for the rest of the run, named in the final summary as unshipped). In Return-to-Caller Mode do not ask and do not edit the file — return `status: blocked` naming it, so the user's WIP stays intact and commit-or-stash-and-rerun is a clean recovery.

3. **Create Task List** _(skip if triage already built one or routed as Trivial)_ — use the platform's task-tracking capability when available (`TaskCreate`/`TaskUpdate`/`TaskList` in Claude Code, `update_plan` in Codex, or the equivalent elsewhere), and follow `references/work-intake.md` for how tasks are derived, named, and ordered. If no such capability exists, continue without simulating a task list in chat.
