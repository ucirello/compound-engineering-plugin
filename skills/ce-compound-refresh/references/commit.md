# Describing and publishing the refresh

Skip if no files changed. Use `jj status`, `jj diff`, `jj log -r '::@'`, and `jj log -r 'trunk()..@'` to understand the working-copy change, unrelated changes, recent description style, and whether the work belongs to an existing change stack. Keep **only** the files this refresh modified in the described change; Jujutsu has no staging area, so use filesets when unrelated working-copy changes must remain in a new change. The description must summarize the refresh outcomes and follow the repository's convention without copying a fixed example. Based on https://go.dev/wiki/CommitMessage and on past commit messages that you can see in `git log`, compose commit messages adherent to the present standards.

Non-interactive defaults: when the refresh is directly based on `trunk()` rather than part of an existing change stack, describe the refresh change, create the next empty working-copy change, publish the described change under a meaningful bookmark, and attempt a PR with `gh`; if PR creation fails, report the bookmark. When already on a feature stack, make the refresh a separate described change on that stack. On a Jujutsu failure, put context-appropriate recovery commands in the report and continue. Based on https://go.dev/wiki/CommitMessage and on past commit messages that you can see in `git log`, compose commit messages adherent to the present standards.

Interactive: ask per Blocking questions, with the recommended option first. Offer choices in terms of the observed Jujutsu state: describe and publish a dedicated change for a PR when based on `trunk()`; describe a separate change on an existing clean stack; isolate only the refresh files when the working-copy change also contains unrelated work; or leave the refresh undescribed.
