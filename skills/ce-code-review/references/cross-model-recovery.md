# Cross-model recovery and coverage

Read at Stage 3d for a failed native launch, or at fold-in for a peer without usable output. Preserve the fixed recipient, requested model/tier, adversarial brief, endpoints and read-only boundary throughout recovery. Preserve diagnostics and receipts in the local `.tmp/` run directory before stopping/releasing a launch.

- **Permission denial, unavailable delegation tool, depth limit, or forbidden model override:** classify the actual error separately. Do not retry denied operations, evade nesting through shell/another harness, or assert permission implies capacity. A suitable inherited-model reviewer can cover the lens where delegation is allowed, but missing required cross-model/fixed-route coverage remains incomplete.
- **Capacity backpressure:** collect/release active native launches and retry queued work only if that can recover a slot within the shared deadline. A nesting-depth limit cannot be repaired by waiting for a slot.
- **Launch-infrastructure failure before a launch ID:** retry only the same permitted route for a new, plausibly recoverable error within the deadline; stop when an error repeats. Resolve invocation mistakes without changing recipients or bypassing permissions. If recovery fails, retain the in-process adversarial reviewer in the roster.
- **Started then failed:** preserve terminal state and diagnostics. Same-route bounded recovery is allowed for a new recoverable infrastructure error, never a repeated denial. Mark degraded lens coverage when recovery is the only cover. Never launch both an in-process reviewer and a recovered peer on the same brief.
- **Authentication-shaped failure:** report account remediation only with positive provider-capable dispatch evidence. Otherwise describe the execution-context failure, not a claimed user logout. No-review outcomes take the fallback below.
- **Overload/rate limit:** at most one same-route retry after an explicit provider overload (HTTP 529), within the original budget. After a terminal provider no-review outcome, use the in-process fallback, not a replacement recipient. Max-turn exhaustion also takes that fallback without retry.
- **No-review outcome:** if the failed recipient was not an explicit user preference and another allowlisted, attested-different native model is permitted, disclose one replacement and collect it within the remaining original budget. Never silently switch, and never make a third peer attempt. Otherwise use a permitted in-process adversarial reviewer. Record `peer.outcome: in-process-fallback` and `adversarial lens: in-process fallback (cross-model peer not run: <reason>)`. This covers the lens, not the required cross-model coverage. Do not call it `harness-native fallback`.
- **Ran with malformed/missing output, or uncertain review completion:** record `peer ran, no usable output` with observed diagnostics; do not claim the lens covered. A valid empty findings array is usable output. A timeout, failure or interruption stays visible, never silently vanishes.

Inline or parent-coordinator fallback contributes attributed evidence only where the contract permits it; exclude parent-context passes from independent reviewer counts and agreement promotion. Unmet independence and cross-model requirements remain incomplete even when useful same-model findings exist. Before returning, stop and collect outstanding work using supported native tools, preserve receipts and bounded diagnostic evidence, and name every missing coverage requirement.
