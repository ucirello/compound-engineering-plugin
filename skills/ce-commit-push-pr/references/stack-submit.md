# Opt-in stack construction and submit recipes

Load this file only for requested stack mode or a standing preference. Before ordinary Step 3, run Probe, Topology, and Retrospective construction as needed. Step 5 alone owns publication and PR writes. Use `references/context.md` for every absolute JJ CWD and scoped `gh` call, and `references/gh-stack-cli.md` for GitHub stack operations.

A **residual** is an unresolved item returned to the user or caller instead of guessing.

## Probe

Verify GitHub Stacks access on the exact base repo without switching the workspace. If required stack intent (an explicit stack request or mandatory standing preference) cannot be met, stop with a residual. With soft preference, report the capability blocker and fall back to the ordinary single-PR flow. An auth error, denied capability, or unexpected response is not proof of a standalone PR.

## Topology

- **Named parent PR or branch:** Resolve the PR by exact identity wherever one exists. Inspect its GitHub stack membership without changing the workspace. If the parent is a stack member, preserve that stack and add only above its verified top. A named parent below the top is a residual; never silently move up to a different parent. For a standalone parent, verify its exact `headRefOid` and expected parent bookmark without overwriting a stale or unrelated local name. Use it as an untouched trunk or adopt it as the first layer only if the current user owns that PR and the topology calls for adoption. A branch without a PR can serve only as trunk. If the exact head cannot be fetched by its verified named remote bookmark and is not local, report the blocker; do not substitute a different SHA.
- **Existing stack without named parent:** Resolve the intended feature and its PR first, then preserve the verified GitHub topology. Use the exact current local tip for an owned parent whose verified work is not pushed yet; otherwise fetch and use its verified tracking remote tip. Do not hardcode a remote or replace the parent with the default branch.
- **No verified topology:** Construct layers from the verified default base (or named standalone parent). If the user did not ask for a stack this run and only one logical change or artificial slices are possible, stay single-PR. An explicit stack request remains required intent; if no viable stack can be formed, report the blocker instead of silently using a single PR.

## Retrospective construction

Inspect the complete task-owned change set: committed changes plus pending working-copy changes, minus `exclude:<paths>`. Derive the smallest useful sequence of independently reviewable layers, in dependency order. Use whole files (including both paths of a rename) or existing commit boundaries, not forced hunk splits. If multiple reasonable topologies materially change review boundaries, ask with the bottom-to-top proposal; pipeline returns the proposal as a residual. Ask before a hunk-level split or rewriting published history; pipeline stops, and neither path rewrites other people's commits.

Pin the original working change and feature tip, recording a recovery bookmark before any operation that could move owned original history. If the work started from the default bookmark and no parent was named, use `references/branch-creation.md` to choose the base, including the unpushed-default decision, without switching the workspace for construction. Otherwise start from the exact verified parent chosen in Topology. Do not bring the whole original feature tip into the bottom layer.

For matching existing commit boundaries, create or reuse local bookmarks at the verified layer tips without rewriting them. When reconstructing unpublished work, leave the original workspace and excluded paths untouched. For whole-file groups from the captured source, build off the working copy: `jj new --no-edit <parent-id>`, then `jj restore --from <captured-source-id> --into <new-layer-change-id> -- <exact-owned-filesets>`. Use this only when the source diff for those paths matches the intended layer against the selected parent, including any upstream edits; don't replace new upstream content with an older whole-file copy. Preserve existing commits and contributor credit where applicable, and stop with a residual rather than overriding overlapping work or guessing at authorship. Compose each new layer's description using the full Go and JJ history guidance in `references/commit-and-push.md`, including the plan unit ID when applicable. Use `jj describe -r <new-layer-change-id> -m "<message composed from the standards above>"` and attach a bookmark at the verified resulting commit. Repeat from that exact layer tip. Keep the original source and recovery references.

Before Step 5, verify that each layer has its intended parent, diff, bookmark, and scope and that the top reproduces the entire original intended change set without excluded paths or a conflict. Reuse the original feature bookmark only at an unchanged verified planned tip or for an authorized move permitted by the publication policy.

## Submit (ready / non-draft)

Resolve the `pr_teaching_archive` / `archive:on|off` gate before publication. If archival is on, stop with a residual; the user can rerun with `archive:off`. Do not add archival commits after publication or silently disable requested archival.

1. Re-read the pinned topology and verify all PR identities, exact base/head refs, existing draft flags, push authority, and current remote tips. Do not mark existing drafts ready unless the author explicitly asked for it. Apply the **Project publishing gate** for every exact outgoing state before any external write.
2. Use a single `jj git push` per verified remote with one `--bookmark "exact:<bookmark>"` per authorized layer that needs publishing. Confirm every pushed SHA before opening or registering PRs. If any update failed or is unproven, report exact remote state and stop before further PR writes; don't assume an all-or-nothing push or undo already-published work.
3. Work bottom to top. For a new layer, compose the normal PR title/body against its pinned immediate parent and head via Step 4, then use the apply recipe with the explicit `--base` and `--head` for that layer. Immediately before create, re-run the exact-head duplicate check; never re-create on an ambiguous error. New layers are ready unless requested otherwise or an existing draft was not authorized to become ready; in that case preserve existing drafts and open new layers as drafts. For an existing draft the author explicitly asked to open, re-verify that specific PR and run scoped `gh pr ready <pr-url>`; do not use a blanket ready operation. Existing PRs keep their titles and bodies unless the invocation explicitly authorizes a rewrite; use Step 5's no-op and preservation rules for an authorized rewrite. Never guess the PR from the working copy or silently retarget an existing PR.
4. Register the verified chain on GitHub, or append only the verified new PRs to the existing stack. Re-read the stack and confirm membership, order, SHAs, and draft state. An incomplete stack or remaining draft layers when babysit is on are hard residuals, not a successful handoff. After verification, hand off the bottom open non-draft PR and pass the exact verified stack identity and topology to `ce-babysit-pr`; do not require a local stack checkout.

No earlier step submits, and this skill never merges.
