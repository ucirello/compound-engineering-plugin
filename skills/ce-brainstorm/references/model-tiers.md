# Model Tiers

Read this when dispatching a sub-agent (the Phase 1.1 grounding scout, the Phase 2.6 claim verifier, or the opt-in Slack researcher). Sub-agent dispatch is tiered by task shape, never hardcoded to a model name:

- **Extraction tier** — the grounding scout: retrieval and quoting work. Use the platform's cheapest capable model when the current harness exposes a known override. "Capable" is part of the spec — escalate to the generation tier when the repo is large or the stack obscure.
- **Generation tier** — the claim verifier: evidence-driven mechanical verification. Use the platform's mid-tier model when the current harness exposes a known override. If model names are unknown, omit the override and inherit rather than guessing.
- **Ceiling tier** — the dialogue itself. Questions, approaches, synthesis, and the requirements-only unified plan run in the main conversation on the orchestrator's model; nothing is dispatched for them.

If the user's or project's active instructions or the live prompt name a model for this subagent, use that model instead of the default tier above. They can name it by the subagent's tier, by its prompt-asset name, or for the subagents being dispatched. Without such an instruction, a model configured for this subagent's role takes precedence over the default tier.

Resolve configured model/tier intent through `opencode.models` before using OpenCode's native subagent capability. Skill-explicit delegation satisfies the host's user-OR-skill exception without redundant approval, but never overrides a higher prohibition. Model permission is separate: when the host requires explicit user model selection, omit the optional model argument unless that request exists. Inherit a suitable model and disclose unmet configured intent; inherited/same-model work is not cross-model independence.

**Degradation rule.** When the native subagent capability does not support or permit per-agent model selection, dispatch the scout and verifier on the inherited model and keep their read budgets and output caps — cost control then comes from structure, not tiering. When no native subagent capability is available, do the topic scan inline at Phase 1.1 — still writing the grounding dossier to the workspace-local scratch path, because downstream consumers (the Phase 2.6 verifier, the ce-plan handoff) receive that path — and verify claims inline before the Phase 3 write, with the same budgets. Do not claim independent coverage from inline work where another contract requires it.

Classify actual depth/capacity, permission, model, and tool errors separately: correct a non-denial pre-launch argument rejection once, leave capacity-limited work queued, and use permitted inline degradation for unavailable/failed work. Never retry a denied operation or switch harness to evade it. Record task ID/status and requested versus served model receipts (missing receipts are unverified). See `reasoning-elevation.md` for the global nested-depth setup prerequisite; never mutate host config.
