# Reviewer Dispatch

Read this before dispatching the Step 2 reviewers. It covers what happens when the harness is full, how review agents are released, and the permission mode.

A generic subagent is one whose whole brief is the prompt you send it. When the host's subagent tool makes you name an agent, use only a name you have seen the host list, and list its agents before the first dispatch if you have not. Pick the plain one that adds no role of its own, which still counts as a generic subagent. Never pick a specialist, such as a reviewer or worker agent, whose own role prompt, output format, or tool limits would replace or narrow your prompt.

**Bounded dispatch.** Queue the reviewers and launch only as many as the harness accepts at once. A concurrency or active-agent-limit error means the harness is full, not that the reviewer failed: leave the reviewer queued and retry after a slot frees. Verify effective nesting capacity from the active OpenCode configuration; delegation permission alone does not guarantee remaining depth. Classify actual dispatch errors separately as capacity/depth exhaustion, permission denial, rejected model argument, or missing tool. When a dispatch cannot recover through active work, supported release, or a corrected invocation, run that pass inline using the same prompt asset and disclose the substitution. Do not retry a denied operation or evade a depth limit through shell or another harness. Inline passes do not provide independent reviewer or cross-model coverage; explicitly report any such required coverage as incomplete.

**Agent lifecycle.** Collect terminal outcomes, including failures, before cleanup. Close or release review-owned agents when the harness provides caller-owned cleanup, before refilling slots, advancing stages, or returning. Do not message completed agents with no remaining work. Do not infer released capacity from completion or interruption, or invent cleanup operations.

**Permission mode.** Omit the `mode` parameter on the dispatch call so the user's configured permission settings apply.

**Delegation authority.** This skill explicitly requests the reviewers. Under a host rule allowing delegation requested by the user OR an applicable loaded skill, that request is sufficient; do not demand another user approval. An unconditional higher-priority prohibition or actual tool denial still applies. Merely loading another skill that never requests delegation does not grant permission. Model-selection permission and nesting capacity remain separate checks: follow Step 2's model rules, and never bypass policy with another harness or shell dispatch.
