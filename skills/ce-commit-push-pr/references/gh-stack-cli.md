# GitHub stack integration with JJ-owned revisions

All local topology, revision selection, bookmarks, fetch and push belong to JJ. Do not use `gh stack checkout`, `init`, `add`, `top`, `submit` or other Git-worktree-mutating stack helpers. They are not native JJ operations and may launch Git. Repository-scoped gh calls run from the absolute target workspace root with exported `GIT_DIR=$(jj git root)`.

Use `gh stack <command> --help` to verify the available GitHub-only linking/landing contract before acting. `gh stack link` is intended for externally managed branches, including JJ: it creates GitHub topology, not local tracking. Therefore never subsequently assume `gh stack view`, `submit` or `merge` sees local management state. Verify remote stack membership and order through the supported GitHub API/interface. Do not invent endpoint schemas, parse status prose as topology, or claim success from unverified links. If the installed interface cannot safely support required GitHub-only stack registration or landing without Git execution, return a specific residual; explicit stack intent never silently degrades to unrelated PRs.

Resolve each PR using `gh pr view <number> --json headRefName,headRefOid,headRepositoryOwner,baseRefName,author,url,state,isDraft`. Bookmark names alone are insufficient: verify repository/owner and exact head object ID. Fetch the exact remote bookmark with JJ or use API evidence; if an exact head cannot be retrieved, report that ref and stop rather than substitute another. Never move a colliding local bookmark.

Never `gh pr merge` a stack member as if it were standalone. Landing belongs to `ce-babysit-pr` under explicit `posture:stack-land` or the user, through a verified stack-aware GitHub-only interface. Ordinary publishing does not grant landing authority.
