# Workspace Setup

Read this after input triage identifies code work and before any branch move, implementation edit, worker dispatch, or commit. It covers choosing a writable checkout, clarifying the plan, placing the branch, recording what was already in progress before work began, handling a unit that must edit an already-dirty file, and setting up the task list. Return to the main `SKILL.md` flow: the canonical checkout, the branch, the pre-work paths and commits, the exclusions, and the task state.

## Writable Checkout

Repo-local implementation writes require a writable JJ workspace. Resolve the absolute root with `jj workspace root` and use it as the CWD of every subsequent JJ command for that workspace (`cd` in a shell subshell or set the tool's working directory). If this session has no writable workspace, but the user named a repository and OpenCode exposes an authorized writable JJ workspace for it, use that workspace for verification, commits, and handoff. Otherwise report that no writable JJ workspace is available; do not synthesize edits elsewhere or fall back to Git.

## Prepare the Work

1. **Read Plan and Clarify** _(skip for a bare prompt)_ — read `references/work-intake.md` for how to size the read, what to pull from the plan, and when to stop and ask. Treat the plan as a decision artifact, not an execution script: ask anything unclear before implementing rather than after. **Do not edit the plan body during execution** — progress lives in JJ commits and the task tracker, and legacy `- [ ]` / `- [x]` marks or a `status:` field are not state.

2. **Setup Environment**

   Two things must hold before the first edit: the work has a verified feature identity, and nothing the user did not offer up gets committed or published by this run. Report the selected identity and exclusions in one line.

   **Bookmark.** Resolve the intended remote and default bookmark from the project's conventions and `jj bookmark list --all-remotes`; use confirmed repository metadata when ambiguous. For GitHub CLI, use `(cd "$workspace_root" && GIT_DIR="$(jj git root)" && export GIT_DIR && gh repo view --json defaultBranchRef)`. Use `main` or `master` only when the remote/default identity is corroborated. Look for the invoked feature bookmark on the relevant revision, checking `@-` when `@` is empty; an empty `@` is not a detached Git branch.

   Reuse a verified non-default feature bookmark without renaming it. Otherwise choose an unused feature bookmark named from the plan or work description; never move the real default or an unrelated bookmark. Record pre-work state before fetch or movement. If there is a remote default, fetch the exact confirmed bookmark with `jj git fetch --remote <remote> --branch <exact-pattern>`, then resolve its full revision. Start above that revision only when the starting history has no local-only commits, the workspace is clean, and the move loses no user state (`jj new <verified-base>` if a new working change is needed). Otherwise preserve the existing working-copy tree and ancestry (no stash or reset); if committing would rewrite a user-owned or immutable change, stop rather than moving it. Create the feature bookmark at the verified starting committed revision with `jj bookmark create <feature> -r <verified-base>`, and verify it with `jj bookmark list <feature>`. Keep the bookmark on the last accepted commit only; advance it after each owned commit once its old target and the new ancestry are verified.

   Reuse verified existing isolation rather than creating another canonical workspace. Create a separate canonical workspace only when the user asked for `ce-worktree` or the multi-PR path calls for one; isolated workers follow their separate dispatch contracts. Update the default bookmark only with explicit current-session authority.

   **Pre-work scope.** Record `jj status`, `jj diff -r @ --summary` (including newly snapshotted user files), and the full starting revisions. For a verified mutable working change, pre-existing committed history starts at its parent; otherwise use the verified committed revision. Check `jj log -r '<verified-remote-default>..<verified-committed-head>'` for pre-existing local-only commits; without a verified remote base the answer is unknown. None of that pre-work scope is yours to commit or publish. Work-owned path-limited commits exclude unrelated WIP; pass every remaining pre-work path to shipping as `exclude:<paths>`, and use local-only `ce-commit` if the publishing rule in `references/shipping-workflow.md` requires it.
   - If a unit needs an already-dirty file, ask once before touching the file whether to include the user's changes or leave it excluded and unshipped. In Return-to-Caller Mode do not ask or edit; return `status: blocked`, naming the collision and how to rerun after the user handles it.

3. **Create Task List** _(skip if triage already built one or routed as Trivial)_ — use the platform's task-tracking capability when available (`TaskCreate`/`TaskUpdate`/`TaskList` in Claude Code, `update_plan` in Codex, or the equivalent elsewhere), and follow `references/work-intake.md` for how tasks are derived, named, and ordered. If no such capability exists, continue without simulating a task list in chat.
