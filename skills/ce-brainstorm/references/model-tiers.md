# Model Tiers

Read this when dispatching a sub-agent (the Phase 1.1 grounding scout, the Phase 2.6 claim verifier, or the opt-in Slack researcher). Sub-agent dispatch is tiered by task shape, never hardcoded to a model name:

- **Extraction tier** — the grounding scout: retrieval and quoting work. Use the cheapest capable model when a native override is permitted and the model is known. "Capable" is part of the spec — escalate to the generation tier when the repo is large or the stack obscure.
- **Generation tier** — the claim verifier: evidence-driven mechanical verification. Use the mid-tier model when a native override is permitted and the model is known. If model names are unknown, omit the override and inherit rather than guessing.
- **Ceiling tier** — the main conversation. Questions, synthesis, and the requirements-only unified plan stay on the orchestrator's model. Ordinary approach generation stays there unless the explicit elevation route in `references/reasoning-elevation.md` applies.

If the user's or project's active instructions or the live prompt name a model for this subagent, it takes precedence over the default tier above. They can name it by the subagent's tier, by its prompt-asset name, or for the subagents being dispatched. Without such an instruction, a model configured for this subagent's role takes precedence over the default tier. Use active config layering from `SKILL.md`, and `opencode.models` to discover permitted model IDs rather than guessing or dispatching through another harness.

**Delegation is separate from model override.** This loaded skill explicitly requests native scout, verifier, and opt-in Slack researcher dispatches. That satisfies a user-or-skill delegation rule, but never overrides an unconditional prohibition, actual denial, or missing tool. If the host requires an explicit user request for a model override and none was given, omit the `model` argument. Inherit when the session model can meet the task's requirements; retain budgets and output caps and disclose unmet configured tier or fixed-model intent. A fresh same-model verifier is a separate reader, not cross-model coverage. If a required model cannot be served, say the fixed route is incomplete; do not label inline work or another model as that route.

**Peer receipts.** Keep each worker's task/session ID when available, role, requested/inherited model, terminal outcome, and any runtime model receipt in the run's local scratch. The request is not proof of which model served. If a fixed route's receipt mismatches, discard that result for the route; if the receipt is absent, do not assert verified fixed-model or cross-model coverage. Separately verify the returned dossier or verdicts before counting the task as usable.

**Degradation rule.** Use the OpenCode V2 depth/config discovery procedure in `references/reasoning-elevation.md`; configured depth and capacity remaining in the current session are not permission. Classify the actual error: depth/capacity, delegation denial, model-argument rejection, missing tool, or other launch failure. Correct a permitted malformed pre-launch invocation once; if only the optional model argument was rejected, inherit on that corrected invocation only when allowed and suitable. Await already-queued work within the available native bound; do not launch a duplicate, retry a denial, or evade a depth limit. When no permitted scout/verifier can run, do the topic scan inline in Phase 1.1 (still write the grounding dossier for the verifier and `ce-plan` handoff, provided local scratch is available), and verify claims inline before Phase 3 with the same budgets. Report that independent verifier coverage was unavailable; the inline check is not a fresh-context pass.
