# Cross-model adversarial recovery

Read this after an attempted launch failed, or after terminal collection yielded no trusted result. Classify from observed native diagnostics; never treat a receipt, permission error, timeout, unverified output, or absent artifact as completed review. Preserve one shared deadline from `references/cross-model-review.md`, the fixed endpoints, read-only boundary, and brief. Resolve/stop any outstanding launch before entering another branch.

- **Delegation prohibition, permission denial, exhausted nesting limit, or absent native tool:** distinguish them using the observed error. Do not retry denied operations, make another harness do them, or treat permanent depth limits as temporary concurrency. Use a permitted local native reviewer only where it can actually launch; otherwise name lost independent coverage. A forbidden model override is separate: an inherited reviewer can cover the local lens where permitted, not an unavailable fixed different-model pass.
- **Recoverable infrastructure or capacity:** on slot backpressure, wait for permitted active work to release a slot within the shared bound. Otherwise retry the same sanctioned route only for a new, plausibly recoverable infrastructure failure with time remaining; stop on a repeat. Before any launch succeeded, finish this recovery before finalizing the roster. After launch, recover only when the earlier attempt is terminal and there is evidence it did not review; any resulting coverage is explicitly degraded. Do not silently substitute scope/model/provider or weaken restrictions.
- **Model or effort refused:** a configured or user-named model or effort is never silently swapped. Name what was refused, any actual availability evidence, and the coverage gap. Only an editorial default may use the single allowed same-route/same-family replacement from the native catalog (prefer the mapped alternate where applicable) after an observed refusal. A host-policy rejection is not a provider refusal. An unsupported editorial Codex effort may be dropped once only if legal and the required tier remains satisfiable; disclose the actual variance or record the unmet tier. This consumes the one replacement.
- **Provider overload/rate limit or max turns:** on explicit overload (HTTP 529), at most one same-route retry under the same deadline; otherwise do not retry the peer for rate/capacity or max-turn exhaustion. Restore the permitted local reviewer when the terminal diagnostic establishes no usable review. Do not switch recipients for these cases.
- **Did not review:** pre-egress route failure, authentication failure, or proven quota/incompatibility without review. Report the actual issue, not a guessed logout; only attribute authentication to the user's account when the provider-capable context or provider response establishes it. At most one replacement recipient when the preference was not explicit in conversation, another attested-different installed native route is allowlisted, and the shared bound still permits it. Resolve, sanction and disclose that route before sending; never use a third peer. Otherwise dispatch the permitted local `adversarial-reviewer`. Record `adversarial lens: in-process fallback (cross-model peer not run: <reason>)` and `in-process-fallback` only if that reviewer actually returns usable findings.
- **Unknown whether a review ran, untrusted artifact, or terminal unusable output:** record `failed` or `no-usable-output` as appropriate and name the actual reason. Do not rerun on another peer route just because output was lost. A full review may report its other coverage; focused review needs a usable separate review, so after terminal collection it may use the local native fallback or otherwise reports Not ready. Inline work in the parent is not that fallback. Never claim verified cross-model corroboration from a local fallback, even though it covers the adversarial lens.

Peer context is read-only inspection of the captured tree; native policy still governs tools, and sending review context to a provider is an external disclosure. Availability trouble is never permission to add recipients, reveal more source, enable tools, or use an unverified model as though it had served.
