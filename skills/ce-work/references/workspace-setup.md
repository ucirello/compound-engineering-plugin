# Workspace Setup

Read this after input triage identifies code work and before any branch move, implementation edit, worker dispatch, or commit. It covers choosing a writable checkout, clarifying the plan, placing the branch, recording what was already in progress before work began, handling a unit that must edit an already-dirty file, and setting up the task list. Return to the main `SKILL.md` flow: the canonical checkout, the branch, the pre-work paths and commits, the exclusions, and the task state.

## Writable Checkout

Repo-local implementation writes require a writable JJ workspace. Resolve its absolute `workspace_root` with `jj workspace root` from the candidate directory before treating it as the project. If the user named a repository and the harness exposes a writable remote repo-work surface, use its verified JJ workspace as canonical. Otherwise report that no writable workspace is available; do not synthesize repository edits in scratch. Run every subsequent JJ command from its target absolute root, e.g. `(cd "$workspace_root" && jj status)`; never use `jj -R` as a cwd substitute. File paths returned by commands stay repository-relative. Repository-scoped GitHub commands use `(cd "$workspace_root" && GIT_DIR=$(jj git root) gh ...)`.

**Isolation first.** Detect existing harness/run-owned isolation before creating anything. Reuse a verified existing workspace under its existing name, even if nondated; never rename/recreate it to enforce naming or colocation. Prefer harness-native colocated JJ creation and adoption/session move when available, respecting its ownership/lifecycle. For newly created `ce-worktree` isolation, request and verify one identity `YYYYMMDD-<meaningful-kebab-case-slug>` for both JJ name and destination basename. Capture the local creation date once; derive the slug from task, PR or revision (`20261008-fix-email-validation`, `20261008-pr-214`, `20261008-review-efcb657`). Normalize caller-supplied names without double-prefixing, check registrations and destination collisions, and append `-2`, `-3`, etc., never random/PID/timestamp substitutes. Retain the selected identity on retry/resume/midnight. Keep PR/source bookmarks unchanged.

For a fresh caller-selected name, remove any existing date prefix before normalizing its meaningful slug to lowercase kebab case and adding the captured creation date exactly once. For a persisted retry/resume identity, use the recorded name unchanged. Check both `(cd "$workspace_root" && jj workspace list)` and the exact destination before creation; advance collision suffixes without overwriting files or registrations.

Only when isolation is authorized and not already provided, use the verified base and an absolute owned destination under the source workspace's local `.tmp/` parent: `(cd "$workspace_root" && jj workspace add --colocate --name "<dated-identity>" --revision "<verified-base>" "<absolute-owned-destination>")`. From the new absolute root run `jj git colocation status` and verify its exact base before editing. Move/adopt the active OpenCode session through its native capability when this becomes the primary root. Unsupported harness creation/naming/colocation is a compatibility blocker through the safe decision path, not permission to bypass ownership, reset state, or use Git-only isolation. An existing isolated workspace retains its name and state; report unmet compatibility without modifying it. Native concurrent workers may use verified harness isolation or the shared-wave contract, not an unauthorized manual workspace.

Retirement uses the safeguards in `cross-model-execution.md`: stop workers, move session to survivor, verify exact name/path/ownership, prove required integration, preserve/read back evidence and recovery references, inspect tracked/conflicted/ignored/untracked content and authorization, then `jj workspace remove` from the surviving absolute root. Verify deregistration and directory disappearance; preserve failures without force deletion. `workspace forget` is unregister-only, preserving files. Completion is not removal authorization.

## Prepare the Work

1. **Read Plan and Clarify** _(skip for a bare prompt)_ — read `references/work-intake.md` for how to size the read, what to pull from the plan, and when to stop and ask. Treat the plan as a decision artifact, not an execution script: ask anything unclear before implementing rather than after. **Do not edit the plan body during execution** — progress lives in JJ changes and the task tracker, and legacy `- [ ]` / `- [x]` marks or a `status:` field are not state.

2. **Setup Environment**

   Two things must hold before the first edit: the work lands on a feature bookmark/change, and nothing the user did not offer up gets committed or published. Routine already-authorized placement needs no second approval; preserve existing state and disclose the placement.

   **Bookmark.** Determine the default from repository metadata; for GitHub use `(cd "$workspace_root" && GIT_DIR=$(jj git root) gh repo view --json defaultBranchRef)`. Otherwise use a verified `main` or `master` bookmark. Inspect `(cd "$workspace_root" && jj bookmark list)` and the exact `@`/`@-` revisions; JJ need not have a current branch.

   If default-bookmark safety is uncertain or no feature bookmark is identified, create a unique task-derived feature bookmark, without moving the real default. Fetch a known remote with `(cd "$workspace_root" && jj git fetch --remote origin)` when applicable. Use the exact fetched default revision when the current ancestry has no local changes beyond it; preserve the current ancestry when local changes must remain visible or no remote exists. Do not abandon dirty/user-owned state to change bases; retain it and use the safe blocker path if placement cannot be separated. Verify bookmark/revision placement after creation. An empty `@` above a verified head is already aligned.

   Otherwise continue on the invoked feature bookmark without renaming it or asking. New primary isolation requires this session's `ce-worktree` authorization; configured cross-model units use the bounded isolation contract. Never advance the real default without explicit authorization.

   **Pre-work scope.** Before editing, record `(cd "$workspace_root" && jj status)` and `(cd "$workspace_root" && jj diff --summary)`, inspect untracked/ignored inventory separately, and compare current ancestry with the exact remote default via JJ log (unknown without a remote). None of that pre-existing state is yours to publish. Preserve it untouched, without stash/reset/discard. Enforce this without asking the user to choose:
   - Incremental JJ changes separate only work-owned paths, so untouched WIP never enters a described unit; the standalone handoff passes every pre-work file this run did not commit as `exclude:<paths>`, and ships locally via `ce-commit` when pre-existing unpushed changes are on the bookmark (`references/shipping-workflow.md`).
   - A unit that must edit a file that was already dirty is the one case a commit cannot separate. Ask once, at the first commit that would include such a file, and cover every such file in that one question: commit those files with the user's edits included, or leave them uncommitted (an exclusion for the rest of the run, named in the final summary as unshipped). In Return-to-Caller Mode do not ask and do not edit the file — return `status: blocked` naming it, so the user's WIP stays intact and commit-or-stash-and-rerun is a clean recovery.

3. **Create Task List** _(skip if triage already built one or routed as Trivial)_ — use the platform's task-tracking capability when available (`TaskCreate`/`TaskUpdate`/`TaskList` in Claude Code, `update_plan` in Codex, or the equivalent elsewhere), and follow `references/work-intake.md` for how tasks are derived, named, and ordered. If no such capability exists, continue without simulating a task list in chat.
