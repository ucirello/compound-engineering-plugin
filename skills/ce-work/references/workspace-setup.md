# Workspace Setup

Read this after input triage identifies code work and before any branch move, implementation edit, worker dispatch, or commit. It covers choosing a writable checkout, clarifying the plan, placing the branch, recording what was already in progress before work began, handling a unit that must edit an already-dirty file, and setting up the task list. Return to the main `SKILL.md` flow: the canonical checkout, the branch, the pre-work paths and commits, the exclusions, and the task state.

## Writable Checkout

Repo-local implementation writes require a writable JJ workspace. Resolve the absolute root with `jj workspace root`, verify the workspace registration and `jj git colocation status` from that root, and use that absolute root as the working directory of every repository command below. If the user named a repository and OpenCode exposes an authorized remote repo-work surface with a writable compatible JJ workspace, use that surface as canonical. Otherwise report the blocker; do not synthesize edits in a non-repository scratch directory.

## Prepare the Work

1. **Read Plan and Clarify** _(skip for a bare prompt)_ — read `references/work-intake.md` for how to size the read, what to pull from the plan, and when to stop and ask. Treat the plan as a decision artifact, not an execution script: ask anything unclear before implementing rather than after. **Do not edit the plan body during execution** — progress lives in JJ changes and the task tracker, and legacy `- [ ]` / `- [x]` marks or a `status:` field are not state.

2. **Setup Environment**

   Before editing, record the pre-work scope and identify the feature bookmark. Under `implementation_engine:`, keep discovery read-only until route and journal requirements in `execution-engines.md` and `cross-model-execution.md` are resolved. Use `jj --ignore-working-copy` for history/metadata reads that would otherwise snapshot; compare the on-disk files with the recorded tree rather than assuming that recorded `@` is current. No baseline commands, tests, fetches, or bookmark moves during that discovery. Then take a fresh snapshot and complete environment setup before editing or dispatching.

   **Feature bookmark.** Determine the default branch from repository metadata (for GitHub: `GIT_DIR=$(jj git root) gh repo view --json defaultBranchRef`); use a uniquely evidenced `main` or `master` fallback only if necessary. JJ has no checked-out branch; inspect `jj bookmark list --all-remotes` and bookmark targets around `@` and `@-`. An empty `@` can be directly above the feature bookmark. Keep a verified invoked feature bookmark; never rename it.

   If on default, without an applicable bookmark, or choosing a safe spare, select a fresh feature bookmark from the plan/work description. When a remote default exists, fetch exactly it (`jj git fetch --config git.abandon-unreachable-commits=false --remote origin --branch "exact:$default"` with the name safely encoded as an exact pattern) and resolve `$default@origin` to one full commit ID. Use that base if the current committed tip is its ancestor; retain the current committed tip if local commits must remain visible or there is no remote. For a clean checkout use `jj new "$verified_base"` as needed; for dirty `@`, preserve its tracked tree delta and ordinary untracked/ignored files, and reparent only when the exact pre-work delta can be verified uncompromised and no unrelated bookmark or work is rewritten. If that cannot be proven, stop rather than overwrite or stash user work. Create the new bookmark on the verified parent with `jj bookmark create "$feature" -r "$verified_base"`; then verify its exact target and working-copy ancestry. Keep the real default bookmark unmoved unless the user explicitly directed working on it in this session.

   Use canonical isolation only when already supplied, requested this session (`ce-worktree`), or when `references/multi-pr-delivery.md` builds an isolated PR group. Worker isolation is separately governed by `references/execution-strategy.md` and `references/cross-model-execution.md`.

   **Pre-work scope.** Before editing, record `jj status`, `jj diff --summary`, and non-snapshotted files relevant to the scope. Record commits present on the verified committed tip but not the remote default (`jj log -r "$remote_default..$committed_tip"`, or "unknown" without a remote). Nothing in that set is yours to commit or publish. Enforce this without asking the user to choose:
   - Use exact work-owned filesets for incremental commits; never include untouched WIP. The standalone handoff passes every pre-work file this run did not commit as `exclude:<paths>`, and ships locally via `ce-commit` if the bookmark includes pre-existing unpushed commits (`references/shipping-workflow.md`).
   - At the first commit that would include an already-dirty file, ask once for all such paths: commit with the user's edits included, or keep them uncommitted (an exclusion for the rest of this run). In Return-to-Caller Mode do not ask or edit such files; return `status: blocked` naming them so the user can preserve their work separately before retrying.

3. **Create Task List** _(skip if triage already built one or routed as Trivial)_ — use the platform's task-tracking capability when available (`TaskCreate`/`TaskUpdate`/`TaskList` in Claude Code, `update_plan` in Codex, or the equivalent elsewhere), and follow `references/work-intake.md` for how tasks are derived, named, and ordered. If no such capability exists, continue without simulating a task list in chat.

## Isolated Workspaces

Follow [JJ's workspace lifecycle](https://docs.jj-vcs.dev/latest/cli-reference/#jj-workspace). Detect isolation first: confirm the workspace registration/name, absolute root, colocation status, and the exact intended committed base (an empty `@` directly above it is expected for a newly created workspace). Reuse verified existing isolation with its existing name; don't rename, recreate, or change its colocation to make it match new-workspace rules. An incompatible base, dirty dependency, or unsupported colocation is a blocker for that route; use only a permitted shared/serial path or report the blocker. Never assume a harness workspace started at the source session's base.

For a new workspace, capture the local date once (`date +%Y%m%d`) and derive a meaningful lower-kebab slug from the task, PR, revision or group, e.g. `20261008-fix-email-validation`, `20261008-pr-214`, `20261008-review-efcb657`. Normalize any supplied name without duplicating the date prefix. Preserve PR/source bookmark names. Use the same dated name for JJ registration and the destination basename, under the selected ignored local `.tmp/` parent (for cross-model work, keep manual destinations under `.tmp/rocketclaw/ce-work/<run-id>/workspaces/`, separate from receipts). Check both registration and path, including symlinks; suffix `-2`, `-3`, etc. on collision. Record and reuse the selected name across retries, resumes and midnight. If a retry retains the old workspace for recovery, do not overwrite it; a distinct attempt needing new isolation uses its own recorded collision-safe identity.

Use the harness lifecycle when it owns isolation. Request supported colocated JJ isolation at the verified base with the chosen name/path and verify the returned identity; unsupported registration/naming/colocation is a compatibility blocker, not permission to bypass lifecycle. For user-requested `ce-worktree`, hand off the chosen identity and base to that skill. When this workflow explicitly permits inline provisioning, use:

```bash
(cd "$source_root" && jj workspace add --colocate --name "$workspace_name" --revision "$verified_base" "$absolute_destination")
(cd "$absolute_destination" && jj git colocation status)
```

Verify exact registration, root and base before edits. Where the active session is meant to enter the isolated workspace, adopt it with native OpenCode `opencode.session.move` and verify the effective directory from the moved session; setting a shell working directory alone does not move a harness session. For delegated workers, use only a native capability that actually binds the worker to the verified directory. Missing/denied adoption is a blocker, not a reason to mutate a different workspace.

## Retire a Run-Owned Workspace

Only remove an exact, authorized run-owned workspace. Stop or await workers, leave its directory and move any active OpenCode session to a verified surviving absolute root. Check exact registered name/path, ownership and current references, and prove integration when required. Retain recovery bookmarks and copy required receipts/logs outside the destination, then read them back. Inspect tracked changes and conflicts plus ignored and left-untracked files; removal snapshots working-copy state, but does not protect ignored or remaining untracked content. Never remove unrelated, non-disposable, ambiguously owned or still-referenced content.

Respect the harness's ownership contract. When removal belongs to this workflow, run `(cd "$surviving_root" && jj workspace remove "$verified_name")`; completion alone does not authorize removal. Verify **both** deregistration and path disappearance (including any remaining symlink). On any warning or partial failure, preserve what remains, report the blocker and do not force-delete or switch to another removal mechanism. `jj workspace forget` is only for unregistering while preserving files. Handle bookmark cleanup separately and preserve best/archive/recovery bookmarks and any needed references.
