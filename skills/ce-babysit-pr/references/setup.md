# Step 1 detail: forge check, PR resolution, chain classification, checkout, watch mode

## Prerequisites

The loop runs `gh`, `jj`, and a bundled Python helper against a local workspace with filesystem access. A harness without those cannot run this skill — say so and stop rather than half-running. Resolve the absolute target workspace root once; every JJ subprocess runs with that root as cwd. Before every repository `gh` operation, from that root set `GIT_DIR=$(jj git root)`; never use `gh pr checkout` or another Git-backed checkout/transport command. Pass `BABYSIT_WORKSPACE_ROOT` to helpers and execute their shell examples from that root.

For deep native delegation, document (never modify the host here): discover the effective config directory with `opencode debug paths` / `opencode debug paths config`, then merge `experimental.subagent_depth` of at least 3 into the existing `opencode.json` or `opencode.jsonc` (normally under `~/.config/opencode`). Preserve sibling fields and higher integers, create no competing file, and ensure higher-precedence configuration does not lower it. Plugin installation or shipped package configuration alone does not enable this.

## Step 1: Confirm GitHub, resolve the PR, pick an execution mode

**GitHub only.** This skill and everything it delegates to speak GitHub's API (`gh`, review threads, Actions). With the backing-store environment above, `gh repo view` succeeding is the positive signal, including GitHub Enterprise. On failure inspect `jj git remote list` from the absolute root. GitLab, Bitbucket, any other forge, or an unresolved repository means stop and explain that ce-babysit-pr is GitHub-only.

Then resolve the target PR from the argument (number/URL) or verified current bookmarks. `@` may be an empty change above the remote branch's PR commit: before concluding that no PR or work exists from `@`, inspect `@-`, resolve that parent's bookmarks, remote branch and associated PR, and continue when eligible. Only after these checks establish that no open PR exists, report and stop. Resolve draft state with the PR. For an automatic calling-skill handoff without an explicit user watch-mode token, this check must be the plain read `gh pr view --json isDraft`, run before any bootstrap — never `snapshot --start-invocation`, which creates a new invocation and would supersede a watch a user explicitly authorized on that draft. A draft target reports its draft status and stops here, before any bootstrap or watcher, per the "Draft PRs are opt-in" boundary. On user-invoked runs the first snapshot's emitted `pr_is_draft` serves as the ongoing signal.

**Check that auto-merge can arm before watching CI.** When the PR expects auto-merge — a check on it arms auto-merge, or the user or calling skill said auto-merge should land it — read the base repository's setting with `gh api repos/<base-owner>/<base-repo> --hostname <host> --jq .allow_auto_merge`. If it is `false`, no CI outcome can merge this PR: report that the repository setting Settings > General > Pull Requests > "Allow auto-merge" is off, and stop before any bootstrap or watcher. In `mode:pipeline` that report is the structured return `{ status: "needs-human" }` from `references/pipeline.md`, with one residual whose `decision_context` names the setting. Changing the setting is the user's call, not this skill's. Once it is on, an auto-merge check that already failed stays red until its job is re-run; Step 5 of the tick handles that.

**Automatically classify the target's PR chain; never rely on the user to announce a stack.** The first snapshot and every later poll probe the read-only local manager with `gh stack view --json`, accepting it only when its branch list contains the target PR. If that cannot prove membership, the helper uses a read-only GraphQL fallback. A successful null stack means `pr_chain.manager_status == "absent"`. The specific stack-field schema-unavailable response also means `"absent"` only when a separate read-only lookup resolves the repository's default branch; auth, transport, rate-limit, malformed, other GraphQL, or failed default-branch probes mean `"probe-error"`. When no manager is confirmed, ordinary open-PR base/head relationships distinguish an independent PR from a manual dependency chain. Discovery never runs `gh stack checkout`, imports a stack, switches branches, or changes remote state.

**Only when the fresh snapshot has `manager_status == "confirmed"` may stack-wide continuation activate; no other classification authorizes it.** A manual dependency chain never activates stack-wide continuation: keep it target-local even when its base/head topology resembles the manager's ordered branches. `probe-error` also stays target-local and mutation-conservative until a later snapshot positively confirms the manager. Discovery still runs for every babysit — posture does not disable confirmed-manager detection or Step 7 upstack maintenance.

For a confirmed managed stack, inspect the manager's ordered entries once before choosing the active layer; this is a read-only look at the order, not multi-PR monitoring. Resolve **posture** per the table in `references/stack.md` before any review/CI work. If posture is still `target` and the requested middle PR has an unsettled downstack layer, offer once to begin at the lowest unsettled non-draft layer and proceed upward (`stack-ready`), with target-only as the alternative; do not silently redirect review/CI work to another PR. If posture is already `stack-ready` or `stack-land` and the requested PR has an unsettled downstack layer, begin at the lowest unsettled non-draft layer without asking (downstack-to-upstack). If all downstack layers are settled, begin on the requested PR. When the requested PR already looks ready or later settles under `target`, offer once to continue to the immediate open non-draft upstack layer if it needs work (accepting selects `stack-ready` for the rest of the run). That one-time offer expands the babysit scope on an already confirmed managed stack — it is **not** a proactive suggestion to create or adopt PR stacks. An explicit request to babysit the managed stack counts as `stack-ready` acceptance, so do not ask redundantly. In `mode:pipeline`, which cannot ask, continue beyond the requested PR only when the invocation already supplied `posture:stack-ready`, `posture:stack-land`, or equivalent stack-wide scope; otherwise return the next candidate as a residual.

Once `stack-ready` or `stack-land` is in effect, that posture authorizes babysitting each layer of the confirmed managed stack in turn without asking again at each layer. Keep one active PR target and one watcher. At each transition: revalidate manager membership and ordered state, stop the old watcher, switch/check out the next immediate layer, then initialize its own snapshot state with `--continue-invocation` and the same three recorded values on the flags the first snapshot used — `--invocation-id "$RUN_INVOCATION_ID" --session-started-at "$RUN_STARTED_AT" --invocation-budget-seconds "$RUN_BUDGET_SECONDS"` (the anchor flag is `--session-started-at`, not `--invocation-started-at`) — plus `--continue-dead-time-seconds <prior layer's `invocation_dead_time_seconds`>` so the shared active-time budget carries the suspended time already excluded on earlier layers (each layer's state dir accumulates its own dead time, so without this the new layer would count that prior suspend as active) — **and re-state the same `posture:` value on the continue invocation**. The invocation budget is not renewed per layer. Never skip past a draft or enter it unless the user explicitly included that draft; never advance past a layer with a `needs-human` blocker. Stop at the first draft outside scope, human-blocked layer, end of the stack, budget, or user stop. Reconfirm `manager_status == "confirmed"` before every cross-PR transition — loss of positive confirmation ends stack-wide continuation rather than degrading into manual-chain behavior.

**Old-PR intake comes before the checkout gate.** On a fresh invocation, run `references/intake.md` here. Its assessment only reads, so a PR you cannot push to still gets a verdict; a Rework or Close verdict stops (or returns, in `mode:pipeline`) before any snapshot or watcher. A user request to take the PR over goes to `references/takeover.md` instead of the gate below.

**Verify exact PR identity and workspace alignment before delegated mutation.** Resolve the PR's head repository, `headRefName`, `headRefOid`, fork status and `maintainerCanModify`; verify the matching named remote URL and exact local/remote bookmarks using `jj git remote list`, `jj bookmark list --all-remotes` and an exact `jj git fetch --remote <verified-remote> --branch exact:<headRefName>`. Never rename the PR bookmark or infer push authority from SHA equality. Pass the verified repository, bookmark, remote and OID to every delegate, which pushes only that bookmark. Missing, denied or unknown authority safely stops; offer takeover when appropriate.

An empty `@` directly above the exact pushed PR head is already aligned, not no-work. Inspect `@-`, its bookmarks/remotes and eligible open PRs even when `@` has no diff or description; do not require a bookmark on `@` itself. Before changing alignment inspect `jj status`, conflicts, tracked changes and ignored/untracked files separately. Preserve all such work. A clean workspace may align with `jj new <verified-head-oid>` without another approval, but never reset dirty/conflicted/ignored work or guess at a moved head. Detect existing isolation first and reuse it unchanged. If new isolation is required, follow ce-worktree's native lifecycle: one persisted local-date `YYYYMMDD-meaningful-kebab-slug` identity for name and basename under the existing local `.tmp`, collision-checked against registrations and destinations; from the source absolute root run `jj workspace add --colocate --name <identity> --revision <verified-base> <absolute-destination>`, then verify `jj git colocation status` there. Harness lifecycle takes precedence; inability to supply the required identity/colocation is a safe blocker.

Then decide **how the watch sustains itself** — a skill can't be re-invoked by magic once its turn ends, so *you* set up the loop. **The default is a self-sustaining, in-session watch: you do not do one tick and hand back a resume command.** Read `references/watch-loop.md` once here for the mechanics; later steps cite its sections rather than re-reading it. Then:

**User-runnable resume syntax.** Whenever this skill prints or copies a resume invocation, default to `/ce-babysit-pr <url>` and, when the run posture is not `target`, append the same `posture:stack-ready` or `posture:stack-land` token so checkpoint / durable / session re-entry keeps stack scope. Use `$ce-babysit-pr <url> [posture:…]` only when the active host is Codex or explicitly documents dollar-prefixed skill invocation. Render only the invocation as inline code and output one form only.

- **Self-sustaining in-session watch (default).** Keep monitoring in the current session until a stop condition is met. Run `pr-snapshot watch`, the deterministic change detector, and wait for its `BABYSIT_WAKE` output using the harness's tools. The detector polls without agent tokens; each wake returns control to this agent for one tick of judgment and sub-skill calls, followed by re-arming the detector. Never collapse those judgments into a shell script. `references/watch-loop.md` defines scheduling and wake handling.
- **Checkpoint.** Use checkpoint mode only when the user requests it or the harness cannot keep the session active while waiting for the detector’s output. Run exactly one tick, persist, report, and print the resume invocation. Say monitoring is paused. Never fake a loop with a foreground `sleep` or by ending the turn and promising to continue.
- **Pipeline** (`mode:pipeline`, set by an orchestrator like `lfg`) — run **bounded synchronous ticks in-line**: the orchestrator is the scheduler, so loop ticks yourself (snapshot → act → re-snapshot) until the **pipeline stop** (Step 3), then return. Fully non-interactive. See `references/pipeline.md` for what differs — a different stop condition, residuals returned in the structured result, and a structured return — and read `references/watch-loop.md` for its bound.

**Durability.** The in-session watch is session-bound; if the session closes, re-invoking with the host-rendered resume syntax resumes cleanly (state is fully persisted on disk). For an unattended watch that must outlive the session (days), move to a durable scheduler where one exists — Grok `scheduler_create --durable`, or a cron running `<harness-cli> exec '<host-rendered resume invocation>'` — accepting that a fresh headless run reconstructs from disk and loses this conversation's context (persist consequential decisions so it does not re-litigate). If the user passed a mode, honor it; otherwise pick per harness capability, state it in one line, and proceed.
